# Mall procedural recreation fidelity notes

This note records the source-side contract for recreating the Luminary mall in browser-native Three.js geometry. The target is the scene at `/view/default-event#/mall`; it must not depend on the GLB at runtime. The checked-in GLB remains a useful visual reference, but it is not an adequate source of object identity because the exporter merges source meshes.

## Source and coordinate contract

The reference scene is `assets-source/scenes/atrium/backups/luminary-galleria-before-floorplans.blend`, SHA-256 `92bcbf50fea02f656e328314521940ff1799810d3ebe68dc14596ba0b5ad7a5f`. `assets-source/scenes/atrium/export_original_mall.py` opens this checkpoint and checks its hash before and after export. It counts 11,259 geometry objects of types MESH, CURVE, FONT, and SURFACE. The current GLB has 76 batched meshes and is 17,845,376 bytes.

The exporter converts Blender coordinates for view/light metadata as `(x, z, -y)`. Its geometry batching is done before that axis conversion: category comes from the object's collection (`P1 |` means garage, `LUM |` means exterior, otherwise interior), and the spatial cell is `(floor(world_x / 32), floor(world_y / 32), floor(world_z / 4.4))`. It converts curves, text, and surfaces to meshes, which bakes the source outlines and modifiers, then joins by category and cell. It parents the batches under `Mall_exterior`, `Mall_interior`, and `Mall_garage`. The current page hides exterior and interior roots for garage views and hides only the exterior root for atrium view.

For browser-native geometry, retain a stable catalog record for every source object before batching. At minimum each record needs the exact source name/ID, category, source world transform, effective world bounds, source geometry kind, source material-slot names, and either a geometry recipe or a reference to a shared geometry plus per-object transform. Store enough provenance on each generated batch or instance to map it back to all contributing catalog IDs. The existing GLB has discarded this name mapping, so it must be captured from the `.blend` during export/catalog generation; do not attempt to infer it from joined GLB mesh names.

World bounds should be measured after evaluating modifiers and converting curve/font/surface geometry, in Blender world space, before applying the `(x,z,-y)` mapping. Preserve the source origin and object transform separately from the evaluated bounds. For visibility/culling, bounds of packed batches must be the union of their actual source members; do not cull based on a coarse mall-wide bound. Use the same category/cell partition as the exporter unless measurements show a better partition that still preserves tight bounds. Keep all original catalog IDs even when the render representation shares or merges GPU buffers.

## What the source builders actually create

`refine_parking.py` is the primitive and material helper source reused by both `refine_vehicles.py` and `refine_luminary_exterior.py`. Its helpers create arbitrary custom meshes, beveled boxes with weighted normals, cached cylinders with smooth quad sides and flat caps, rods oriented between endpoints, poly or auto-handled Bézier curves with bevel depth, and torus meshes. Its material helper sets base color, roughness, metallic, coat weight/roughness, and emission; a noise node can add procedural surface variation. These details matter at silhouette and close-up scale, especially in parking and vehicle views.

`refine_vehicles.py` creates three master families (SUV, EV, Sedan) and linked instances for the fleet. The body is a longitudinal loft through eight cross sections with a ten-point profile, gets boolean wheel arches, then bevel and weighted-normal modifiers. Windows, A/B/C pillars, seats, dashboard, wipers, grille, lights, registration, four tyres per vehicle, brake rotors, rims, split spokes, lugs, and calipers are separate parts. This is not a generic car primitive: preserve each vehicle's class, dimensions, color, trim, and instance transform from source data.

`refine_luminary_exterior.py` imports the parking helpers by AST and uses them to create the envelope, canopy, public realm, landscape, arrival roads, services, lights, and cameras. `build_atrium.py` adds the interior furniture and planting. Its geometry includes eased furniture boxes, reused cylinders/spheres, tapered line segments, table details, leaf crowns, and FONT objects with extruded/beveled glyphs. The standalone floor-plan fitting script also emits custom planar meshes and beveled box pieces. Treat any geometry not covered by the shared helpers as authored topology, not permission to replace it with a blockout.

## Materials, alpha, normals, and browser parity

The source uses Principled BSDF values, including coat, emission, and transmission. For example, lobby glazing has transmission `0.93`; dark automotive glass has roughness `0.095`, metallic `0.3`, and transmission `0.7`. The current Three material loader determines shadow casting from `material.transparent` or positive `transmission`; all meshes receive shadows. Keep these semantics aligned when replacing the loaded model. Do not convert transmission glass into generic 0.5-opacity alpha: the two shading paths sort, write depth, and respond to environment lighting differently.

The GLB exporter is allowed to convert/triangulate geometry and export only glTF-representable material data. Blender procedural nodes, bevel/weighted-normal behavior, fonts, and unsupported shader nodes may be baked, reduced, or omitted during conversion. Browser-native recreation will use Three's renderer and material model, so matching numeric base/roughness/metalness/emission is necessary but cannot promise pixel identity under different environment maps, tone mapping, shadow filters, transparency sorting, and renderer versions. Report this as a rendering-pipeline limit; do not claim exact pixel parity from source-parameter matching alone.

Normals and winding are part of the fidelity contract. Preserve the source face winding through the Blender-to-web rotation `(x,z,-y)` (a proper rotation with determinant `+1`), transform normals consistently, preserve smooth/flat face flags, and retain weighted-normal results or reproduce their visible shading. Avoid global `DoubleSide` as a repair for flipped geometry. For flat labels and decals, retain whether the source face is one-sided or deliberately double-sided.

FONT geometry needs special treatment. The source builders use `C:/Windows/Fonts/bahnschrift.ttf` and `segoeuib.ttf` in parking, while atrium text uses object bodies with extrusion and bevel. A browser's installed fallback font can change glyph widths and silhouettes. Preserve the exact source-generated glyph outlines and extrusion result as native buffer geometry, or use the exact font files and parameters with licensing review before copying font binaries into public assets. Do not substitute a visually similar system font for authored text when the goal is source-faithful geometry.

## Recommended representation without runtime GLB

Use the source scene as the geometry oracle and port reusable recipe families into pure geometry builders only where the source topology and parameters are known: boxes, cylinders, rods, curves, tori, lofts, and authored polygon meshes. The exported scene data stores evaluated custom topology in ordinary position/normal/UV/index buffers; browser code can construct native Three.js `BufferGeometry` from these fields without shipping or loading a GLB. It should not replace the 11,259 source identities with a hand-designed mall blockout. For repeated geometry, use shared buffers and `InstancedMesh` where material and render flags match. For static unique geometry, merge by category/cell/material/render-state after preserving per-object catalog records. Sharing a geometry among many Mesh objects alone does not reduce draw calls. Text, transparency, and transmissive objects may require separate batches because their depth sorting, shadow flags, or material groups differ.

Use a per-category spatial index for batch bounds and visibility. Each source object remains queryable by exact ID, while rendering uses cell-sized batches or instances. The batch builder should be deterministic and should fail if any source record has no output geometry or maps to more than one output owner unexpectedly. Keep light/camera metadata separate: the GLB intentionally omits cameras and lights, while `luminary-original.json` stores the six view presets and source light metadata.

## Coverage validator contract

The focused validator should load the source catalog and generated browser catalog, then compare exact ID sets and per-ID ownership. It should report missing IDs, unexpected IDs, duplicate ownership, category mismatch, transform/bounds drift, geometry-family mismatch, material-slot drift, and batch bounds that fail to contain member bounds. Bounds tolerances must be explicit and small in metres; no tolerance should allow omitted geometry. A renderer-count check belongs at the batch level, not the number of catalog entries.

Do not synthesize a passing coverage manifest from the current 76 GLB meshes: those batches cannot reveal the 11,259 source names, object origins, or individual bounds. The source catalog must be generated from the original `.blend` before those names are lost.
